# Quorum-Replicated Log (Go, 单机本地模拟)

一套完全本地可运行的**多数派复制键值存储**：在一个进程内启动多个 Raft 副本，
用内存传输模拟真实集群（含崩溃、重启、网络分区），实现持久化日志、崩溃恢复、
并发提交的一致结果，并对每类失败给出**可区分的拒绝原因**。

只依赖 Go 标准库，无需任何外部服务、网络端口或凭据。

```
go run ./cmd/kvdemo          # 端到端演示
go test ./...                # 全部单测/集成测试（打印输入与判定依据，加 -v 查看）
go test -race ./...          # 竞态检测
go test -count=20 ./kvserver # 压力/抖动重复
```

## 1. 架构

| 包 | 职责 |
|---|---|
| `wal/` | 定长帧 + CRC32 + `fsync` 的预写日志；打开时检测并截断尾部残缺/损坏帧；hardstate 帧（term/vote）与数据帧分离；日志重写（处理冲突后缀） |
| `store/` | 确定性键值状态机：`Set`/`Delete`/`Incr`；按**日志索引**与**客户端 RequestID** 双重幂等 |
| `raft/` | Raft 共识核心：选举、多数派日志复制、当前任期提交规则、领导权确认（ReadBarrier）、no-op 提交旧任期条目、崩溃恢复 |
| `cluster/` | 单进程多副本模拟：进程内传输、统一 tick 驱动、`Crash`/`Restart`、`Partition`/`Heal` |
| `kvserver/` | 将 Raft 与每个副本的状态机粘合：JSON 命令、领导重定向+重试、幂等去重、线性读/显式 stale 读 |
| `cmd/kvdemo/` | 本地可运行的端到端演示程序 |

每个副本是一个**单线程事件循环** goroutine：所有状态修改（追加日志、推进
commit、角色转换）都在该循环内串行完成；RPC 只入队为任务。因此并发的
`Propose` 按入队顺序获得一个确定的全序，无数据竞争（`-race` 验证）。

## 2. 复制与提交语义

- **多数派可见性**：写入先持久化到 Leader 本地，再并行 `AppendEntries`；
  只有**含 Leader 自身在内的多数副本**持久化后，条目才推进 `commitIndex`
  并按顺序回调状态机，之后才对客户端返回成功。多数派之外的写入绝不提交。
- **当前任期提交规则（Raft §5.4.2）**：Leader 只能用**本任期**条目推进提交点；
  旧任期条目只能被一个已提交的本任期条目**传递性提交**。新 Leader 当选立即
  追加一条 no-op 来确定本任期提交点。这保证被罢免 Leader 留下的未提交旧
  任期写入不会由它自己在之后直接提交。
- **领导权更替使旧写入失效**：
  - 发现更高任期 → 该副本退回 Follower，在途提案以 `STALE_TERM` 拒绝；
  - Leader 连续一个选举超时联系不到多数派 → 主动下台，在途提案以
    `NO_QUORUM` 拒绝（任期并未确认结束，客户端可凭幂等 ID 重试）；
  - 向非 Leader 提案 → `NOT_LEADER`，错误中带 `LeaderHint` 供重定向。
- **拒绝原因可区分**（`raft.RejectCode`）：

  | Code | 含义 |
  |---|---|
  | `NOT_LEADER` | 该副本不是 Leader（含 `LeaderHint`） |
  | `STALE_TERM` | 提案任期已结束（发现更新的领导者/任期） |
  | `NO_QUORUM` | 多数派未确认（副本不可达，或 Leader 失联下台） |
  | `STALE_READ` | 读屏障无法确认当前领导权，拒绝返回可能过旧的值 |
  | `REPLICA_CLOSED` | 副本已关闭/崩溃 |
  | `EMPTY_REQUEST` | 空写请求 |

- **并发写入**：事件循环串行追加 → 每个并发写获得唯一递增索引（确定全序）；
  各副本按同一日志顺序回放，状态最终收敛。

### 关于“被拒写入”的结局（重要契约）

对返回超时/`NO_QUORUM`/`STALE_TERM` 的写请求，标准 Raft 的结局是
**未知（unknown）**，而不是“确定未发生”：若持有该未提交条目的旧日志副本在
网络恢复后恰好赢得下一任期，它的 no-op 可能传递性地提交该旧条目（Figure 8）。
本实现严格遵守这一点。正确的客户端用法：

1. **所有写请求携带 `ClientID + RequestID`**：无论同一请求被重试多少次，
   状态机只执行一次并返回首次结果（计数器不膨胀）；
2. 需要确定状态时，用**新的请求**重建（覆盖任何未知结局），再做线性读确认。

在多数派不可用期间，线性读同样被拒绝（`STALE_READ`），因此未知结局也不可能
通过读路径泄漏。

## 3. 持久化与恢复保证

- **持久化顺序 == 提交顺序**：日志只追加，`Append` 后 `fsync`；提交按索引
  严格递增地应用到状态机。
- **WAL 帧格式**：`magic | kind | uint32 长度 | payload | uint32 CRC32-IEEE`。
  CRC 覆盖 kind+长度+payload。term/vote 用独立的 `kindHardState` 帧追加，
  崩溃后取最后一帧。
- **尾部残缺不静默应用**：打开日志时从头逐帧校验。第一个损坏帧（部分写入
  `partial-frame`、魔数错误 `bad-magic`、长度非法、CRC 不符 `crc-mismatch`）
  起到文件尾的所有字节被**一次 `truncate + fsync` 截断**，并在
  `RepairReport` 中报告截断字节数与原因；之后的数据不回放、不应用。
- **已提交数据完整恢复**：崩溃重启后从磁盘重建日志与 hardstate，追上 Leader
  后按序回放已提交前缀；也可独立以多数派身份重新参选。
- **重复回放幂等**：状态机对 `index <= lastApplied` 的回放返回缓存结果且
  不改状态；相同 `RequestID` 标记为 `Duplicate`。崩溃恢复反复执行同一条已
  提交记录，键值与计数器都不变化、不膨胀。
- **冲突后缀重写**：Follower 收到与本地冲突的日志时，用原子 `Rewrite`
  （写临时文件 + `fsync` + `rename` + 目录 `fsync`）丢弃冲突后缀，保留
  当前 term/vote。

## 4. 读取一致性

- `LinearizableRead`：先由 Leader 发起一轮**新鲜的多数派心跳（ReadBarrier）**
  确认自己仍是 Leader，再读本地已应用状态。无法获得多数派确认时以
  `STALE_READ` **明确拒绝**，绝不返回旧值。
- `StaleRead(id, key)`：只读指定副本的本地状态，返回值永远带 `stale=true`
  标记——允许本地读，但结果被显式标注为可能过旧。

## 5. 关键配置项（`raft.Config`）

| 字段 | 默认值 | 说明 |
|---|---|---|
| `ElectionTimeoutMin/Max` | 120ms / 240ms | 选举超时区间，每轮在区间内随机，避免选票分裂 |
| `HeartbeatInterval` | 30ms | Leader 心跳/复制周期（由统一 tick 驱动） |
| `RPCTimeout` | 60ms | 单轮复制等待慢/死副本的上限，超时即不计入本轮 |
| `ProposeTimeout` | 1s | 客户端等待提交上限，超时后按任期状态给 `STALE_TERM`/`NO_QUORUM` |
| `Apply` | — | 提交回调（索引, term, data），须对重复索引幂等 |
| `Dir` | — | 每个副本独立的持久化目录（`wal.log`） |

`cluster.WithTickStep`（默认 5ms）控制模拟时钟推进粒度。调大这些时长可在
慢机器上获得更宽松的时序；所有数值都不影响正确性，只影响演示速度。

## 6. 本地验证

```bash
go vet ./...
go test -race ./... -v          # 查看每个用例打印的输入与判定依据
go run ./cmd/kvdemo             # 7 个场景的端到端演示
```

测试覆盖（均在 `*_test.go` 中打印输入与判定依据）：

1. `wal`：追加/重开顺序一致；**尾部少 3 字节被截断**；**CRC 损坏被截断**；物理截断
2. `store`：Set/Get/Delete；**同索引重复回放计数器不膨胀**；**相同 RequestID 重试只执行一次**；旧索引回放不倒退
3. `kvserver` 集成：
   - 多数派提交 + 线性读返回新值
   - 多数派之外写入被拒（`NO_QUORUM`/`NOT_LEADER`，可区分）
   - 多副本**崩溃-重启**后状态一致收敛
   - **日志尾部残缺**（砍掉 wal 字节）后重启自动修复、已提交前缀不丢
   - 分区后旧 Leader 的在途写入失效（`STALE_TERM`/`NOT_LEADER`），heal 后用新请求重建并收敛
   - **超时重试**相同请求 3 次只生效一次
   - **80 个并发提交**在 5 副本上确定排序、全部收敛
   - 无法确认领导权的读被**拒绝**；本地读被**标记 stale**
   - 无多数派时写不可见、读被拒；恢复后新写覆盖未知结局并收敛

## 7. 范围与边界

- 这是教学/验证用的紧凑实现：进程内传输、单一日志文件、无快照（日志不压缩）、
  无成员变更与流水线批处理；Raft 的核心安全性（选举限制、提交规则、日志匹配）
  均已实现并由测试覆盖。
- 模拟“崩溃”= 不做优雅关停地丢弃内存状态（`Crash`）；`Stop` 才是优雅关闭。
